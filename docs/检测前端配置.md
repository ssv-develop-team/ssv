# 检测前端配置

## 边界

当前仓库没有独立的一方 Web 前端。本文中的“检测前端”指 `runner/` 提供的实时检测入口、本地图像显示、RTSP 输出和检测框 overlay；它负责从 RTSP 输入构建 GStreamer pipeline，不负责网页播放、浏览器控制台或远程 API。

## 配置文件

复制模板后只编辑本地副本：

```bash
cp config/ssv.example.yaml config/ssv.yaml
```

runner 的搜索顺序为：

1. `./ssv run --config PATH`。
2. `SSV_CONFIG_PATH` 指向的文件。
3. 项目根目录 `ssv.yaml`。
4. `config/ssv.yaml`。
5. `/etc/ssv/ssv.yaml`。

`config/ssv.example.yaml` 只用于复制，不会被自动加载。YAML 版本固定为 `2.0`，C++ runner 对未知字段和错误类型严格失败；配置路径、临时 Redis 覆盖和调试日志可用环境变量，运行参数本身应写进 YAML。

## 输入与解码

当前阶段只配置一个 H.264 8-bit RTSP source；事件规则正文不嵌入 source 配置：

```yaml
sources:
  - id: "camera-01"
    uri: "rtsp://localhost:8554/test"
    codec: "h264"
    protocols: "tcp"
    latency_ms: 200
    decode:
      mode: "auto"
      device: "auto"
```

| 字段 | 说明 |
| --- | --- |
| `sources[0].id` | source 标识，进入日志和发布消息 |
| `sources[0].uri` | 可访问的 RTSP 地址；仓库不会启动 MediaMTX |
| `sources[0].codec` | 当前要求 `h264` |
| `sources[0].protocols` | RTSP transport，常用 `tcp` |
| `sources[0].latency_ms` | GStreamer 接收延迟 |
| `sources[0].event_rule` | 可选的兼容 metadata；缺失不会阻止 source 启动，也不承载规则正文 |
| `sources[0].decode.mode` | `auto`、`vaapi`、`nvdec`、`software` |
| `sources[0].decode.device` | `auto`、`drm:/dev/dri/renderD<N>` 或 `cuda:<N>` |

规则正文由 Agent 的 `agent.knowledge.rules_dir` 管理，默认递归读取
`agent/knowledge/rules/`。每个 `.md` 或 `.txt` 规则文件使用 `kind: rule`、`rule_id` 和
`version` front matter；同一 `(rule_id, version)` 不能重复。规则正文不会写入 Redis，Agent
会把显式规则身份转换为精确检索条件，没有身份时按 `event_type` 或检测事实寻找候选。
`rule_facts`（如果上游仍提供）只是待核验的事件事实，不是规则文件的替代品。

Agent 取证按检测 episode 聚合：同一 source、规则和 `stream_generation` 的连续事件不会
重复生成视频。episode 由 tracker 的 `NEW`、`MATCHED`、`LOST`、`DEAD` 状态推进；Agent
不使用 IoU 重建人员身份。episode 关闭后，Agent 以首次和最后一次 `source_pts` 观测加
上 pre-roll/post-roll 生成一个 `[source_pts_start, source_pts_end)` 缓存窗口。

`auto` 会按实际元素选择 VAAPI、NVDEC 或 software；显式硬件模式不可用时直接失败，不会静默切换。解码 profile 和 ONNX Runtime profile 是两个独立选择。

## SSV 短时证据缓存

需要让 Agent 从 runner 自身取证时，在输入解码前的编码码流分支启用短时缓存：

```yaml
evidence_cache:
  directory: "/var/lib/ssv/evidence-cache"
  segment_duration_ms: 10000
  retention_ms: 120000
  max_bytes_mb: 512
```

始终启用的缓存位于 `h264parse` 后的 encoded branch，由 `tee -> queue -> splitmuxsink` 写入原始 H.264 分段；检测、跟踪、显示仍使用独立的解码分支。每个 source 使用独立目录，分段文件关闭后才写入 finalized sidecar，sidecar 同时记录 `stream_generation` 和 source PTS 区间。Agent 的 `recording_evidence` 只读取这些已闭合、与事件 generation 匹配的分段。

| 字段 | 说明 |
| --- | --- |
| `evidence_cache.directory` | SSV 与 Agent 共享的绝对目录；取证 worker 要求它位于 `agent.evidence_roots` 内 |
| `evidence_cache.segment_duration_ms` | 单个分段时长，最小 1000 ms |
| `evidence_cache.retention_ms` | 按墙钟清理的保留时间，不得短于分段时长 |
| `evidence_cache.max_bytes_mb` | 缓存目录容量上限，达到上限时删除最旧的 finalized 分段 |

该分支的运行时收尾是 best effort：分段关闭后的 sidecar 写入失败或缓存分支运行中发生错误时，runner 会记录缓存不可用，但不阻塞解码、推理、跟踪和 Redis 发布。首次启动时如果缓存目录无法创建，或目标环境缺少已配置的 GStreamer 元素，builder 会报告 capability failure 并拒绝启动；这能避免启用后却静默丢失全部证据。缓存不是长期录像，远程 WVP RTSP 只需能被 `sources[0].uri` 访问，不要求 WVP 或 MediaMTX 与 runner 在同一台机器；真正的长期留存仍由 WVP/NVR/MediaMTX 负责。

启用后需要目标环境提供 `splitmuxsink`（通常来自 GStreamer `multifile` 插件）及其 MP4 muxer 依赖。可用性检查：

```bash
gst-inspect-1.0 splitmuxsink
gst-inspect-1.0 mp4mux
```

缓存目录和 Agent 的 `evidence_roots` 必须使用同一共享文件系统；只把远程 RTSP 地址写入 `sources[0].uri`，不会让 Agent 直接读取远程视频服务。

## 显示与 overlay

```yaml
display:
  enabled: true
  backend: "auto"
  # 仅 backend 为 rtsp 时使用；auto 不会自动发布到此地址。
  rtsp:
    location: "rtsp://127.0.0.1:8554/ssv"
    # true 时将检测框直接烧录进远端视频；默认关闭。
    burn_in_overlay: false
    # true 时直接转发输入 H.264，跳过输出分支的解码和编码；不能与烧录同时开启。
    encoded_passthrough: false
  fps: 30
  gl_backend: "auto"
  overlay:
    enabled: true
    font:
      face: "regular"
      size: 12
    motion_prediction:
      enabled: true
      max_horizon_ms: 300
```

| 字段 | 取值或作用 |
| --- | --- |
| `display.enabled` | 是否启用输出分支；GTK backend 创建本地窗口，RTSP backend 创建发布分支 |
| `display.backend` | `auto`、`gtkglsink`、`gtksink`、`rtsp`；`auto` 只在 GTK backend 之间选择 |
| `display.rtsp.location` | `rtsp` backend 的发布地址，必须是 `rtsp://` 或 `rtsps://` |
| `display.rtsp.burn_in_overlay` | 是否将检测框、类别、置信度和 track ID 绘制到 RTSP 视频像素；默认 `false`，开启时要求 `ssvoverlay` |
| `display.rtsp.encoded_passthrough` | 是否从 depay/parser 后直接转发 H.264；默认 `false`，不能与 `burn_in_overlay` 同时开启 |
| `display.fps` | 输出分支的 drop-only 上限 |
| `display.gl_backend` | `auto`、`x11`、`wayland` |
| `display.overlay.enabled` | 是否在独立 GTK 框层绘制检测框 |
| `display.overlay.font.*` | 框层文字样式 |
| `display.overlay.motion_prediction.*` | 仅影响显示时的短时位置预测 |

`gtkglsink` 是严格的 GL/DMABuf 路径；`gtksink` 是显式的 SystemMemory 兼容路径。选择 `rtsp` 时，默认输出分支经过 SystemMemory/I420、H.264 编码、RTP 打包后连接 `rtspclientsink`，不初始化 GTK，也不创建本地窗口。开启 `display.rtsp.encoded_passthrough: true` 且关闭烧录时，输出从 depay/parser 后经过有界 queue、RTP 打包直接发布，保留源视频的时间戳、帧率和编码参数，`display.fps` 不参与该分支限流；若同时启用推理，解码仍由分析分支使用。RTSP 默认不带检测框；只有 `display.rtsp.burn_in_overlay: true` 会在编码前插入 `ssvoverlay`，接收端因此能直接看到框和标签。它复用 `display.overlay.font` 与 `display.overlay.motion_prediction`，但 `display.overlay.enabled` 仍只控制 GTK 独立绘制层。overlay 不回写 tracker、Redis 事件或证据。

命令行覆盖只存在于本次进程：

```bash
./ssv run --headless
./ssv run --display
./ssv run --display --overlay
./ssv run --display --display-backend gtkglsink
./ssv run --display --display-backend gtksink
./ssv run --display --display-backend rtsp
```

`--display` 与 `--headless` 互斥；`--display-backend` 接受 `gtkglsink`、`gtksink` 或 `rtsp`。选择 `rtsp` 时，发布地址仍须在 YAML 的 `display.rtsp.location` 中配置；没有桌面会话时可以使用 RTSP backend 或 `--headless`，不要把 GTK 问题误判为模型或 Redis 问题。

## 推理配置

正式推理路径直接读取原始 ONNX。模型必须有唯一的静态 `float32 [1,3,H,W]`、NCHW 输入，输出必须为静态 float32 tensor：

```yaml
inference:
  enabled: true
  analysis_fps: 15
  model:
    path: "models/yolov8n.onnx"
    family: "yolo"
    output_format: "yolov8"
    label_map: "config/model-labels/coco80.txt"
    preprocess:
      color_order: "rgb"
      resize: "letterbox"
      execution: "auto"
      normalization:
        scale: 0.00392156862745098
        mean: [0.0, 0.0, 0.0]
        std: [1.0, 1.0, 1.0]
  runtime:
    type: "onnxruntime"
    providers:
      mode: "auto"
    device_id: 0
    precision: "auto"
    cpu_threads: "auto"
    cache:
      enabled: true
      directory: ""
  confidence_threshold: 0.5
  target_class: "person"
```

- `analysis_fps` 是推理/跟踪/发布分支的抽帧上限；`0` 表示不限流，但仍不积压旧帧。
- `runtime.type` 为 `onnxruntime` 时使用 `.onnx`；TensorRT 实验路径使用 `.engine` 和配套 `manifest`。
- `providers.mode: auto` 使用构建 profile 的 Provider 链；固定顺序时使用 `explicit` 并填写 `order`，例如 `tensorrt`、`cuda`、`openvino`、`migraphx`、`cpu`。
- `target_class` 为空字符串表示不过滤类别；名称必须存在于 `label_map`。
- `preprocess.color_order` 为 `rgb` 或 `bgr`；`resize` 为 `letterbox` 或 `stretch`。
- `preprocess.normalization` 按 `(pixel * scale - mean) / std` 计算；旧的 `/255` RGB 语义对应上面的默认值。
- `preprocess.execution` 为 `cpu`、`cuda` 或 `auto`。ONNX Runtime 当前使用 CPU 预处理，直接 TensorRT 才可能使用 CUDA 预处理。
- 运行时不要求 `ssv.wrapper.*` metadata，也不会生成中间模型；不会根据文件名或 ONNX metadata 猜测颜色和归一化语义。

`--output-format` 支持 `yolov8` 和 `yolo_nx6`。后者要求原模型输出已经是 `[1,N,6]` 的 `x1,y1,x2,y2,score,class_id`。模型导出和验证的更多说明见 [YOLO 推理链路说明](yolo推理链路说明.md) 和 [安全帽模型验证说明](安全帽模型验证说明.md)。

TensorRT 是独立的实验路径。插件只加载已经构建好的 `.engine`，不会在运行时把 ONNX 转成 engine；engine 应在最终运行机器上从同一个原始 ONNX 构建：

```bash
trtexec \
  --onnx=models/yolov8n.onnx \
  --saveEngine=models/yolov8n.engine \
  --fp16

./ssv model manifest \
  --model models/yolov8n.onnx \
  --engine models/yolov8n.engine \
  --output models/yolov8n.engine.json \
  --precision fp16 \
  --tensorrt-version 10.16.1.11 \
  --cuda-runtime-version 13020 \
  --compute-capability 8.9
```

manifest 会记录 engine SHA-256、原始 ONNX SHA-256、engine 输入 I/O、精度、TensorRT/CUDA 版本和 compute capability；加载时拒绝 hash、版本、设备或输入契约不一致的产物。manifest 不承载颜色顺序、归一化、resize 或输出格式。对应 YAML 为：

```yaml
inference:
  model:
    path: "models/yolov8n.engine"
    manifest: "models/yolov8n.engine.json"
    family: "yolo"
    output_format: "yolov8"
    label_map: "config/model-labels/coco80.txt"
  runtime:
    type: "tensorrt-engine"
    device_id: 0
```

## 跟踪与发布

`ssvpub` 始终把传输层 `type: detection` 写入 Redis；只有配置了可选 `event_rule` 时，才会
额外写入 `event_type`、`severity`、`rule_id`、`rule_version` 和 `rule_facts`。Agent 不会把
传输层 `type` 伪装成业务事件类型；缺少显式 `event_type` 时保持未知，并由规则目录检索候选。
规则 RAG 返回的 `rule_citations` 是复验时的候选条款，不能替代或覆盖事件登记事实。历史
Redis 消息不会被回填。

事件中的 `source_pts` 和 `stream_generation` 是精确证据关联的唯一媒体锚点；缺失时不
推导。Agent 的 `get_event` 输出 `episode_id`、episode 状态、关闭原因和冻结证据窗口，
便于排查为什么一条事件尚未取证或为什么多条 Redis 消息只对应一个 clip。

```yaml
tracking:
  enabled: true
  track_threshold: 0.5
  track_buffer: 30
  match_threshold: 0.3
  mock_track: false
  publish_cooldown_ms: 30000
  gmc:
    method: "sparse-opt-flow"
    downscale: 2
```

`ssvtrack` 当前使用 BoT-SORT；`track_id: -1` 表示该对象没有稳定跟踪 ID。`publish_cooldown_ms` 是发布侧的同 source/track 冷却，`0` 关闭发布冷却；它不能把不稳定的 tracker ID 变成可靠业务身份。Agent 消费侧还有独立的 `agent.dedup_*` 兜底配置。

## 环境变量

| 变量 | 作用 |
| --- | --- |
| `SSV_CONFIG_PATH` | 指定 YAML 文件 |
| `SSV_RTSP_URL` | 临时覆盖 `sources[0].uri` |
| `REDIS_HOST` / `REDIS_PORT` | 临时覆盖 Redis 连接 |
| `GST_DEBUG` | 临时覆盖 GStreamer 日志级别 |

模型、runtime、display、tracking 和 RTSP latency 不提供同名环境变量覆盖，以免构建、运行和 Agent 读取到不同配置。

## 启动与排错

```bash
./ssv build --profile cpu
./ssv inspect
./ssv run --headless
GST_DEBUG="ssv*:5,*redis*:4" ./ssv run --headless
```

输出问题排查顺序：先检查 `./ssv inspect`，再根据 backend 检查 `gst-inspect-1.0 gtksink`、`gtkglsink`，或 `rtspclientsink`、`rtph264pay` 和 H.264 encoder；开启 RTSP 烧录时再检查 `gst-inspect-1.0 ssvoverlay`。使用 RTSP backend 时还要确认外部 RTSP server 已创建对应发布路径，并用独立客户端播放发布地址。循环文件以 `-c copy` 发布时，如果码流参考帧或时间戳损坏，软件和硬件 decoder 都可能花屏；更换输出 backend 不能修复输入码流。
