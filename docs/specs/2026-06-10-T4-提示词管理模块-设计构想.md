# T4 提示词管理模块 — 设计构想

> 用于讨论和确认方向，确认后按项目规范输出正式 spec 和 plan。

---

## 一、背景与目标

### 现状

当前 Agent 的"智能"输出全部硬编码：

| 位置 | 做法 | 问题 |
|------|------|------|
| `MockProvider.analyze()` | 4 行 if-else 返回固定 mock 文本 | 接真实 LLM 时全部重写 |
| `ReviewContext.prompt_context` | `"\n".join(lines)` 字符串拼接 | 无角色、无格式约束、无示例 |
| `ContextBuilder._lookup_rules()` | 3 条硬编码规则 | 无法扩展 |

M5 端到端 demo 需要切换到真实 LLM，提示词质量直接决定复核准确率。没有集中管理会导致散落四处、改一处牵全身、无法 A/B 测试、出问题找不到根因。

### 设计目标

- **集中管理** — 所有提示词在一个模块内，改内容不翻代码
- **按策略分离** — 4 条复核策略各自持有独立模板，互不干扰
- **最小侵入** — 不破坏现有状态机和事件模型
- **可调试** — 每次 LLM 调用记录完整 prompt 和 response，方便定位 bad case
- **可演进** — 模板未来可迁至 YAML 文件驱动、向量检索、数据库存储

## 二、核心原则（5 条）

> 这 5 条是设计提示词模块的底层依据，也是评审每次提示词变更的检查清单。
> 原则与各代码模块的对应关系见 [附录 B](#附录-b原则与模块映射)。

### 原则 1：清晰明确，减少歧义

每句话只应有一种合理解读。用精确数值而非模糊词。

- `system.py` — 判断原则使用精确阈值："置信度 > 0.85"，而非"高置信度"
- `templates.py` — 指令用祈使句，任务拆成编号子问题，避免开放式提问

> ❌ "请你看看这个检测结果，给出合理的判断" — "合理"无标准
> ✅ "请判断是否为未佩戴安全帽的违规事件。输出 JSON: `{"is_violation": true/false, "reasoning": "..."}` "

### 原则 2：提供必要的上下文

LLM 不知道管线前面发生了什么，每次调用必须携带全部判断所需信息。

每次复核调用必须携带：视频源、帧编号、时间戳；每条检测的类别、置信度、坐标、跟踪 ID；推断的严重程度和触发原因；相关安全规则片段（如有）；证据文件摘要（如有）。

- `assembler.py` — `_build_event_context()` 展开完整 DetectionEvent
- `templates.py` — `{event_context}`, `{evidence_summary}`, `{rule_snippets}` 占位符
- `system.py` — 内置判断原则作为静态领域知识

### 原则 3：设定具体的要求

模糊要求 → 模糊输出。对格式、长度、风格、精度都要有明确约束。

`SystemPrompt` 中的硬约束：
1. 不在结论中使用"一定"、"肯定"，除非置信度 > 0.95
2. 不确定时设置 `needs_human=true`
3. 结论不超过 200 字
4. 引用检测数据时标注置信度和来源

- `system.py` — `output_spec` 定义 JSON Schema，`constraints` 逐条约束行为
- `templates.py` — 每条模板以编号问题列表收尾，强制 LLM 逐项回应

### 原则 4：给出示例或者参考

Few-shot 比指令描述更直观，是提升输出质量和格式一致性的最有效手段。

- 每条示例的 `expected_output` 与 `output_spec` 格式完全一致
- 示例按策略组织，覆盖 4 条策略各 1-2 条
- 按标签检索最相关示例注入 prompt，避免无关示例撑爆 token
- 后续从真实复核结果中筛选高质量 case 补充

- `examples.py` — `FewShotExample` 标准化结构 + `ExampleBank.select_by_tags()`
- `assembler.py` — 示例注入为 user/assistant 消息对

### 原则 5：分步骤思考

引导 LLM 分步推理（Chain of Thought），比一步出结论更准确、更可解释。

任务模板中的分步引导模式：
- 步骤 1：列出每条检测的关键特征（类别、置信度、跟踪状态）
- 步骤 2：逐一分析可能的误检/漏检原因
- 步骤 3：综合以上给出 JSON 格式结论

- `templates.py` — 任务模板拆为 3 个子问题
- `system.py` — 判断原则按优先级排列（先判置信度 → 再判检测组合 → 最后判跟踪）

## 三、模块设计

### 文件结构

```
agent/src/ssv_agent/prompts/
├── __init__.py      包入口，导出 PromptAssembler / PromptManager
├── system.py        系统提示词 — 角色定义 + 输出格式 + 行为约束
├── templates.py     策略模板 — 4 种策略各含独立任务模板 + 占位符
├── examples.py      Few-shot 示例库 — 标准化示例 + 按标签检索
├── assembler.py     组装器 — 模板 + 示例 + 上下文 → messages
├── logger.py        调试日志 — 记录每次调用的 prompt 和 response
└── manager.py       轻量管理 — 健康检查 + 版本号查询
```

### 各文件职责

#### `system.py` — 系统提示词

定义 Agent 是**谁**、输出**什么格式**、受**哪些行为约束**。这是与策略无关的全局层，相对稳定。

关键属性：`content`（角色+判断原则+注意事项）、`output_spec`（JSON 输出格式）、`constraints`（行为规则列表）、`version`

#### `templates.py` — 策略模板

一种策略 = 一套模板。模板用 `{placeholder}` 占位符，由 Assembler 填充。

| 策略 | 特点 | 占位符 |
|------|------|--------|
| `direct_confirm` | 直接确认高置信度违规 | `{event_context}` |
| `visual_review` | 结合关键帧图像复核 | `{event_context}`, `{evidence_summary}` |
| `rule_explain` | 引用安全规则解释冲突 | `{event_context}`, `{rule_snippets}` |
| `notify_report` | 严重事件生成通知报告 | `{event_context}` |

每条模板自带 `version`、`description`、`changelog`。

**策略专属系统提示**：不同策略对 LLM 的引导侧重点不同。`StrategyTemplateSet` 提供可选的 `system_template` 字段，允许策略在全局系统提示词之外追加策略专属的引导语：

| 策略 | 全局系统提示词 | + 策略专属追加 |
|------|:--:|------|
| `direct_confirm` | 角色+通用判断原则 | "当前事件已被管线判定为高置信度违规，你的默认立场是**确认**，除非发现明确的矛盾信号" |
| `visual_review` | 同上 | "当前事件置信度较低或存在遮挡。重点关注：光照条件、目标遮挡程度、检测框稳定性。低置信度不必然意味着误检" |
| `rule_explain` | 同上 | "当前事件存在冲突信号（head+helmet 同时出现），你需要判断是误分类还是正常佩戴。bbox 重叠程度是关键依据" |
| `notify_report` | 同上 | "当前为严重事件。除复核判断外，你还需要生成面向现场安全员的通知文本，包含时间、位置、违规描述、建议处置" |

> **设计要点**：策略专属提示是**追加**而非替换。全局系统提示词中的角色定义、输出格式、行为约束保持不变。这解决了全局提示"一刀切"无法适应不同策略需求的问题。

#### `examples.py` — Few-shot 示例

Few-shot 示例的结构化存储和检索。

`FewShotExample` 字段：`strategy`、`scenario`（场景描述）、`input_context`（模拟输入）、`expected_output`（期望 JSON）、`tags`（标签）、`quality_score`（质量分）、`source`（manual / real_case）

`ExampleBank` 方法：`select_by_tags(tags, n)` 按标签检索、`top_quality(n)` 取最高质

当前预设 5 条人造示例，覆盖 4 条策略。后续从真实复核结果中筛选高质量 case 持续补充。

#### `assembler.py` — 组装器（模块主接口）

输入 `ReviewContext`，输出标准 messages 列表（兼容 OpenAI / Anthropic 格式）。

**组装流程：**

```
渲染系统提示词 + 策略专属追加
    → 按标签检索 few-shot 示例，注入为 user/assistant 消息对
    → 按策略选择模板，填充占位符
    → Token 预算检查与截断
    → 输出 PromptAssembly（messages + token 估算 + 模板版本）
```

**Token 预算与截断策略：** 当估算 token 数超出 `max_tokens` 阈值时，按以下优先级从低到高逐项裁剪，直到预算达标：

| 优先级 | 内容 | 策略 |
|:--:|------|------|
| 1（最先裁） | Few-shot 示例 | 减少示例条数（从 `max_examples` 递减到 0） |
| 2 | 规则片段 | 精简 `rule_snippets`，只保留与 trigger_reason 最相关的 1 条 |
| 3 | 检测详情 | 精简每条检测的显示字段（只保留 class_name + confidence，去掉 bbox 坐标） |
| 4（不裁） | 系统提示词 | 始终完整保留 |
| 5（不裁） | 事件基本标识 | source + frame_id + timestamp_ms 始终保留 |

`max_tokens` 默认值根据目标模型 context window 设置，可通过 `AgentConfig` 覆盖。截断后在 `PromptAssembly.metadata` 中标记 `truncated: true` 及实际采取的裁剪动作，便于回溯。

**替换关系：**

```
ReviewContext.prompt_context（旧：字符串拼接）
        ↓ 替换为
PromptAssembler.assemble(context) → messages

MockProvider.analyze()（旧：硬编码文本）
        ↓ 替换为
LLMProvider.analyze() → assembler.assemble() → call_api() → parse_response()
```

#### `logger.py` — 调试日志（新增）

每次 LLM 调用记录完整交互，是调试 bad case 的基础设施。

```
PromptLogger
  log_call(assembly, response, latency_ms, model_name) → call_id
  log_error(assembly, error, latency_ms) → call_id
  get_call(call_id) → CallRecord | None
```

`CallRecord` 字段：`call_id`、`timestamp`、`strategy`、`template_version`、`messages`（完整发送的 prompt）、`response`（模型原始返回）、`parsed_result`（解析后的 ReviewResult，如有）、`latency_ms`、`model_name`、`error`（如有）、`truncated`（是否触发截断）

日志输出使用现有 `structlog`，不引入新依赖。`CallRecord` 同时输出为结构化日志字段，支持后续 grep/jq 快速过滤。

> **设计要点**：`PromptLogger` 是调试工具而非业务模块。在 mock 模式下不启用（避免无意义的日志堆积）；在真实 LLM 模式下默认启用，可通过配置关闭。

#### `manager.py` — 轻量管理

当前阶段只做两件事，其余功能按需追加：

- **`validate()`** — 健康检查：所有策略是否都有对应模板？占位符 `{event_context}` 是否在每个模板中都存在？`output_spec` 是否为空？返回 `{valid: bool, issues: [str]}`
- **`get_versions()`** — 返回当前所有组件的版本号快照：`{system: "1.0.0", direct_confirm: "1.0.0", ...}`

以下功能标注为"后续按需实现"，当前不做：
- ~~版本变更历史记录（`record_version`）~~
- ~~全量配置快照（`create_snapshot`）~~
- ~~快照列表查询（`list_snapshots`）~~

理由：M4→M5 阶段提示词仍在快速试错，版本号通过 dataclass 字段手动管理就够用。等提示词内容相对稳定后再补版本管理基础设施。

## 四、VLM 提示词（预留）

T4 spec 已定义 `BaseVLMProvider.review_keyframe(image_path, context)`，用于 `VISUAL_REVIEW` 策略。但当前提示词模块只覆盖了文本 LLM。

**关键差异：**

| | 文本 LLM | VLM |
|------|------|------|
| 消息格式 | `{"role": "user", "content": "text"}` | `{"role": "user", "content": [{"type": "text", ...}, {"type": "image_url", ...}]}` |
| 输入 | 纯文本上下文 | 文本上下文 + 关键帧图像 |
| 输出 | 结论文本 | 视觉复核结论（`ReviewConclusion`） |

**预留方案：**

1. `PromptMessage.content` 类型预留为 `str | list[dict]`，当前用 `str`，后续扩展 `list[dict]` 支持多模态
2. `PromptAssembler` 预留 `assemble_vlm(context, image_path)` 方法签名，当前抛出 `NotImplementedError`
3. VLM 版本的系统提示词和任务模板复用现有 `templates.py` 内容，仅消息构造方式不同

> 本阶段不实现 VLM 提示词组装，M5 接入真实 VLM 时再展开。

## 五、集成方式

### 对现有架构的改动

```
service.py (AgentService.__init__)
  ├── 新增: self._assembler = PromptAssembler()
  ├── 新增: self._prompt_logger = PromptLogger()    （真实 LLM 模式下启用）
  └── （状态机不改，provider 内部自行调用 assembler）

将来新增 LLMProvider(BaseProvider)
  ├── 构造时接收 PromptAssembler + PromptLogger
  └── analyze(context):
        assembly = self.assembler.assemble(context)
        response = self._call_api(assembly.messages)
        self.logger.log_call(assembly, response, ...)    ← 每次调用留痕
        return self._parse_response(response)
```

### 改动范围

| 模块 | 改不改 | 说明 |
|------|:--:|------|
| `models/event.py` | 不改 | ReviewContext 保持不变 |
| `state_machine/` | 不改 | 状态机不感知提示词细节 |
| `providers/mock.py` | 不改 | mock 继续返回硬编码 |
| `context/builder.py` | 不改 | 继续提供 rule_snippets |
| `service.py` | 小改 | 新增 assembler、logger 实例化 |
| `prompts/` | 新包 | 6 个文件（含 logger.py） |
| `providers/llm.py` | 新文件 | 真实 LLM provider（M5） |

## 六、迭代工作流

```
基线建立 → 发现 Bad Case → 诊断定位 → 修改记录 → 对比验证
```

1. **基线** — 预设提示词作为 v1.0.0
2. **Bad Case** — 某类事件复核不准，通过 `PromptLogger` 回溯当时的完整 prompt 和 response，记录事件特征 + 实际输出 + 期望输出
3. **诊断** — 定位根因：系统提示词不清？策略模板引导不对？缺 few-shot？Token 截断丢了关键信息？
4. **修改** — 改对应模块，手动更新 dataclass 版本号，在 `changelog` 字段记一句修改原因
5. **验证** — 用同一个 ReviewContext 跑新旧版本，人工评估；退化则回滚版本号

> **调试技巧**：通过 `PromptLogger.get_call(call_id)` 取出完整 messages，直接在 LLM Playground 里逐条调试，定位是哪一段 prompt 导致了问题。

| 技巧 | 适用场景 | 核心语句 | 模块对应 |
|------|---------|---------|---------|
| **角色设定** | 需要专业深度 | "你是有 X 年经验的……" | `system.py` 角色定义 |

| **思维链** | 推理/判断/分析 | 先在 thinking 中分析再作答 | `templates.py` 分步引导（原则5） |
| **少样本示例** | 风格/格式难以文字描述 | 2-3 个输入→输出例子 | `examples.py` → `assembler.py` 注入 |
| **防幻觉设计** | 事实性/高风险任务 | "只用提供的文档，不确定请说明" | constraints: needs_human=true |
| **提示词链** | 复杂多步骤任务 | 拆分子任务串联 | 状态机 8 状态天然形成链 |
| **元提示** | 不知如何写提示词 | "帮我生成/改进提示词" | 开发工具链（不在运行时） |
| **五段式架构** | 构建完整 AI 应用 | 角色+数据+规则+格式+示例 | 本模块整体架构 |
