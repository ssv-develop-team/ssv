# 硬件能力快照与建链解耦

## 目标

在一次 SSV 运行初始化时探测 GStreamer、推理运行时和相关硬件能力，形成只读的
`SsvCapabilitySnapshot`。本次运行后续的 plan 解析、拓扑构建和 fallback 都使用
这份快照，不在编码、解码或推理分支中重复探测能力。

## 当前问题

当前 `SsvHardwareCapabilities` 既表示探测结果，又直接作为 plan 和 builder 的
临时参数传递。这样虽然实际运行中通常复用了同一份数据，但接口无法表达快照的
所有权，也允许 plan 与 builder 接收不同的 registry。

## 设计

### 能力分层

- `SsvHardwareCapabilities`：底层 probe 生成的原始结果，包括 GStreamer factory
  列表、推理运行时编译能力标志和 ONNX Runtime 已注册 provider 列表。
- `SsvCapabilitySnapshot`：对原始结果的只读封装，提供能力查询接口；创建后不再
  修改。
- `SsvInferencePlan`：从配置和快照解析本次运行使用的推理 backend 和 provider
  输入。模型配置中的 device id 继续由 inference service 消费，不把模型/session/
  cache 的运行时结果伪装成静态能力。
- `SsvEncodePlan`：描述一个输出编码器、编码设备和输入 memory contract。
- `SsvCodecPlan`：同时持有 decoder 与 encoder，并标记是否为同设备硬件配对或
  混合路径。硬件配对优先，混合路径是明确的 fallback，而不是由调用方临时拼接。
- `SsvPipelinePlan`：持有本次运行使用的 `capability_snapshot`，并从快照与配置
  推导 codec、推理 backend、memory caps 和 fallback 策略。

推理 service 接收快照中的 provider 列表副本，`OnnxRuntimeBackend::load()` 直接
使用这份列表进行 provider availability resolution，不再在每次 attempt 中调用
`Ort::GetAvailableProviders()`。provider 的 session 创建、模型契约、cache 命中和
fallback 仍属于 inference service 的运行时初始化，因为这些结果依赖模型、配置和
具体 session。

session 初始化期间读取的 device identity 只用于 cache namespace 和运行时诊断，
不参与 decoder、encoder 或 provider chain 的选择，因此仍由 session/backend 资源
负责，而不是提升为通用的建链能力字段。

### 后端选择

能力快照只负责提供本次运行可查询的静态事实；后端 plan 负责把事实和配置组合成
一条可建链的路径。

编解码选择按以下顺序处理：

1. 若输出不需要重新编码（RTSP encoded passthrough 或非 RTSP 显示），不创建
   `SsvEncodePlan`。前者标记为 `Passthrough`，仍需解码供显示或分析的后者标记为
   `DecodeOnly`，避免把“没有编码器”误写成 software codec pair。
2. RTSP 需要重新编码时，优先选择同一设备上的硬件 decoder/encoder pair；VAAPI
   使用同一 DRM render node，NVDEC/NVENC 使用同一 CUDA device。
   当设备 selector 为 `Auto` 时，保留 `Auto` 并选择同一 backend 的通用 factory
   pair，由 GStreamer 使用同一个默认设备；显式 selector 则复制到 encoder plan
   并在 builder 中校验。
3. 同设备 pair 不完整、设备级 factory 不存在或 pair 的 memory contract 不成立
   时，保留硬件 decoder，切换到 SystemMemory 软件 encoder，形成混合路径。
4. 混合路径仍无法建链时，`decode.mode: auto` 才允许继续回退到软件 decoder；
   显式硬件模式保持严格失败。

NVDEC 的 decode contract 保持 `CUDAMemory`。当下游是 `gtksink`、CPU 推理预处理
或软件 encoder 时，builder 必须显式插入 `cudadownload` 后再进入 SystemMemory
转换链；NVDEC/NVENC 硬件配对则保持 CUDA memory 直达 encoder。

推理选择独立于视频编解码选择。ONNX Runtime/TensorRT 的 backend plan 只使用
快照中的编译能力和 provider 列表；推理 backend 不得通过“当前 decoder 是哪一种”
来推断。

### 生命周期

```text
prepare_run
  -> SsvCapabilitySnapshot
  -> SsvPipelinePlan::resolve(config, snapshot)
       -> SsvCodecPlan
       -> SsvInferencePlan
  -> ssv_inference_service_create(
       config, snapshot.onnxruntime_providers())
  -> SsvPipelineBuilder::build(config, plan, inference_service)
  -> GStreamer pipeline
```

同一次运行的 codec pair fallback、display fallback 或 software decode fallback 只
重新解析配置和 plan，不重新探测 GStreamer registry，也不重新调用 provider
availability probe。codec fallback 只处理 `display.start` / `display.contract` 的
编码分支失败，不把分析或推理 contract 错误误判为 codec 故障。fallback 事件必须
记录原路径和目标路径。

### Plugin 边界

不把 Runner 的 C++ 能力对象作为通用 GObject 指针注入所有 plugin。GStreamer 内置
元素通过已解析的 factory、device 和 caps 工作；SSV plugin 继续接收自身需要的
`source-context`、`inference-service` 和业务配置。能力快照的所有权停留在 Runner /
Pipeline plan 层，inference service 只接收 provider 列表这一项稳定的值类型输入，
避免 plugin ABI 反向依赖 orchestration 类型。

## 接口约束

- `SsvCapabilitySnapshot` 的查询方法为 const，不提供运行时修改能力列表的接口。
- `SsvPipelinePlan::resolve` 只接受 `SsvCapabilitySnapshot`；raw probe 结果必须在
  `prepare_run` 或测试 fixture 边界完成封装。
- builder 不再接收独立的 registry 参数，避免 plan 和 builder 使用不同能力视图。
- 没有有效 snapshot 时，默认构造的 plan 仍可用于纯数据结构测试，但真实运行必须
  经由 `prepare_run` 生成 snapshot。

## 非本阶段范围

- 不实现运行时热插拔硬件或自动刷新能力快照。
- 不把完整硬件快照暴露给 `ssvinfer`、`ssvtrack`、`ssvpub` 或 `ssvoverlay`；
  inference service 只接收 provider 列表。
- 不实现运行时硬件热插拔、设备复位后的能力刷新或跨设备负载均衡。
- 本阶段不把所有 GStreamer element 的 pad caps 预先枚举成完整格式矩阵；设备级
  pair 先由 factory/device 命名和 builder contract 表达，最终能力仍由 negotiation
  验证。
- 不把模型/session/cache 结果提升为全局硬件能力；它们仍由 attempt-owned
  inference service 创建和释放。
- 不声称 factory 存在就等于设备可用；真实 pipeline 仍通过 GStreamer negotiation
  和现有 contract probe 验证运行能力。

## 验收标准

- 能力 probe 在一次运行中只执行一次。
- plan 持有并使用该运行快照，builder 不再接收独立 registry。
- plan 暴露独立的 `SsvInferencePlan` 和 `SsvCodecPlan`；推理选择不依赖 codec
  选择。
- RTSP 重编码优先得到同设备硬件 codec pair；pair 不完整时显式得到混合路径，
  而不是错误地声称硬件编码可用。
- fallback 重试不重新探测能力，且所有 pipeline branches 使用同一能力视图。
- ONNX Runtime provider availability 在一次运行中只探测一次，fallback 重试和
  重新建链复用同一 provider 列表。
- pipeline、runtime、GStreamer plugin 和 Agent 现有测试通过。
