# 硬件能力快照与建链解耦

## 目标

在一次 SSV 运行初始化时探测 GStreamer、推理运行时和相关硬件能力，形成只读的
`SsvCapabilitySnapshot`。本次运行后续的 plan 解析、拓扑构建和 fallback 都使用
这份快照，不在编码、解码或推理分支中重复探测能力。

## 当前问题

当前 `SsvHardwareCapabilities` 既表示探测结果，又直接作为 plan 和 builder 的
临时参数传递。这样虽然实际运行中通常复用了同一份数据，但接口无法表达快照的
所有权，也允许 plan 与 builder 接收不同的 registry。

## 设计

### 能力分层

- `SsvHardwareCapabilities`：底层 probe 生成的原始结果，包括 GStreamer factory
  列表和推理运行时编译能力标志。
- `SsvCapabilitySnapshot`：对原始结果的只读封装，提供能力查询接口；创建后不再
  修改。
- `SsvPipelinePlan`：持有本次运行使用的 `capability_snapshot`，并从快照与配置
  推导 decoder、encoder、推理 backend、memory caps 和 fallback 策略。

### 生命周期

```text
prepare_run
  -> SsvCapabilitySnapshot
  -> SsvPipelinePlan::resolve(config, snapshot)
  -> SsvPipelineBuilder::build(config, plan, inference_service)
  -> GStreamer pipeline
```

同一次运行的 display fallback 或 software decode fallback 只重新解析配置和 plan，
不重新探测 GStreamer registry。

### Plugin 边界

不把 Runner 的 C++ 能力对象作为通用 GObject 指针注入所有 plugin。GStreamer 内置
元素通过已解析的 factory、device 和 caps 工作；SSV plugin 继续接收自身需要的
`source-context`、`inference-service` 和业务配置。能力快照的所有权停留在 Runner /
Pipeline plan 层，避免 plugin ABI 反向依赖 orchestration 类型。

## 接口约束

- `SsvCapabilitySnapshot` 的查询方法为 const，不提供运行时修改能力列表的接口。
- builder 不再接收独立的 registry 参数，避免 plan 和 builder 使用不同能力视图。
- 没有有效 snapshot 时，默认构造的 plan 仍可用于纯数据结构测试，但真实运行必须
  经由 `prepare_run` 生成 snapshot。

## 非本阶段范围

- 不实现运行时热插拔硬件或自动刷新能力快照。
- 不把完整硬件快照暴露给 `ssvinfer`、`ssvtrack`、`ssvpub` 或 `ssvoverlay`。
- 不改变 decoder、encoder、推理 provider 的实际选择优先级。
- 不声称 factory 存在就等于设备可用；真实 pipeline 仍通过 GStreamer negotiation
  和现有 contract probe 验证运行能力。

## 验收标准

- 能力 probe 在一次运行中只执行一次。
- plan 持有并使用该运行快照，builder 不再接收独立 registry。
- 编码、解码、推理 backend 解析结果与现有配置和能力优先级保持一致。
- fallback 重试不重新探测能力，且所有 pipeline branches 使用同一能力视图。
- pipeline、runtime、GStreamer plugin 和 Agent 现有测试通过。
