# 规则目录发现与可选匹配规格

## 背景

旧设计要求每个 `sources[]` 在共享 YAML 中嵌入一份 `event_rule`。这把检测事实、规则身份、规则正文和 Agent 的检索实现绑在同一个 source 配置上：规则版本增加时需要修改运行时配置，规则正文无法独立审阅和版本管理，缺少规则时 Runner 也不能启动。

本规格将规则正文移到 Agent 管理的目录。规则文件递归发现并解析为带身份和版本的只读文档；source 规则引用变为可选上下文。Agent 根据显式引用精确选择规则，没有引用时再根据事件事实检索候选规则。

## 目标

- `sources[].event_rule` 不再是配置加载的必填项。
- 在 `agent/knowledge/rules/` 下保存可版本管理的规则文件和模板。
- 从配置指定的规则目录递归发现 `.md` 和 `.txt` 文件，并以 `(rule_id, version)` 建立稳定身份。
- 本地检索和 Qdrant 入库共用同一规则发现与解析实现，避免两个后端看到不同的规则集合。
- Agent 给复核模型提供规则正文、版本、来源路径和内容哈希，引用可被确定性校验。
- 显式的 `rule_id + rule_version` 走精确过滤；只有 `event_type` 时按事件类型过滤；完全没有引用时只按检测事实召回候选。
- 规则缺失、引用不唯一、检索失败或引用校验失败时保守输出 `uncertain`，不得伪造规则结论。

## 配置契约

```yaml
agent:
  knowledge:
    backend: "local_markdown"
    rules_dir: "knowledge/rules"
    qdrant_path: "data/qdrant"
    qdrant_url: null
    min_score: 0.5
```

`rules_dir` 是相对于 Agent 项目根目录的路径，也可以使用绝对路径。C++ Runner 只校验共享配置结构，不读取规则目录；Agent runtime 将它解析为 `SSV_KNOWLEDGE_RULES_DIR`。规则目录不存在时，local backend 返回明确的空目录结果，Qdrant 入库命令失败并报告路径，不能静默回退到旧的 `agent/knowledge/` 顶层扫描。

`sources[].event_rule` 保留为可选的兼容字段。它可以随事件提供事件类型或外部规则身份，但不再承载规则正文，也不能阻止没有该字段的 source 启动。新配置和模板不依赖该字段。

## 规则文件格式

规则文件使用 YAML front matter，正文从 front matter 结束标记之后开始：

```markdown
---
kind: rule
rule_id: gb26860-helmet
version: v1
event_type: person_without_helmet
severity: high
aliases:
  - 安全帽
---

# 作业现场安全帽佩戴要求

1.1 作业人员应正确佩戴安全帽。
```

规则身份只由 `(rule_id, version)` 决定，不由文件名或目录名猜测。解析器至少保留：

- `rule_id`、`version`、`event_type`、`event_types`、`severity`、`aliases`；
- 规则文件相对于 `rules_dir` 的 `source_path`；
- 规范化后的规则正文 `content`；
- `sha256` 格式的 `content_hash`。

解析器递归读取 `.md`、`.txt`，跳过 `_templates` 和隐藏目录；只有带 `kind: rule` front matter 的文件进入目录。普通 README 等没有 front matter 的文件会被跳过；标记为规则但不完整的文件会报告可定位的解析错误。相同 `(rule_id, version)` 出现两次时，发现失败，不能按文件名随机覆盖。

front matter 不进入规则正文 chunk。chunk metadata 至少包含：

```json
{
  "source": "gb26860-helmet/v1/rule.md",
  "rule_id": "gb26860-helmet",
  "rule_version": "v1",
  "section": "1.1",
  "content_hash": "sha256:..."
}
```

## 检索与复核接口

规则目录发现器是 Agent 内部的深模块接口：

```python
discover_rule_documents(rules_dir: Path) -> tuple[RuleDocument, ...]
```

本地检索器和 Qdrant 入库器只依赖该接口返回的文档，不各自遍历目录。检索过滤键为 `rule_id`、`rule_version` 和 `event_type`；过滤键缺失时不添加对应限制。

`rule_retriever` 工具额外接受 `rule_id` 和 `rule_version` 参数。Agent 复核上下文只把规则正文作为只读证据传给模型，不让模型修改规则文件；prompt 必须展示版本和 hash，结果引用必须同时匹配 `chunk_id`、`source`、`rule_id`、`rule_version` 和 `section`。

## 非本阶段范围

- 不从规则文件自动生成 detector、tracker 或 GStreamer pipeline 配置。
- 不把规则目录复制到 Redis 事件；事件只携带可选身份和检测事实。
- 不让规则解析器执行 Markdown 中的代码、链接或外部网络请求。
- 不在本阶段删除历史 spec/plan；旧文档保留为历史记录，新文档声明其替代关系。
- 不改变证据缓存、Episode 聚合、RTSP sink 或 overlay 的媒体链路。

## 验收标准

1. 只有 `id` 和 `uri` 的 source 配置可以通过 C++ 和 Agent 配置校验。
2. 规则目录可以递归发现多个版本，模板、隐藏目录和非规则文档不会进入检索。
3. 重复规则身份、缺少身份字段和不支持的 front matter 能得到稳定的失败信息。
4. local backend 与 Qdrant ingest 产生相同的来源、版本、hash 和 section metadata。
5. Agent 没有显式规则引用时仍能基于检测事实工作；候选不足时结果为 `uncertain`。
6. 规则版本变化会改变引用和索引身份，不会复用旧版本正文。
