# 证据时间线与受控停机修复

## 背景

2026-10-16 的端到端测试在首条事件发布约三秒后停止 GST，而缓存目标分段为十秒。测试没有等待 MP4 封口及 sidecar 发布，导致证据不可用；这是测试停止条件错误。

延长运行后又复现了两个独立的时间线问题：分析分支的有界 leaky queue 在丢帧后设置 `DISCONT`，被共享时间线误判为源 epoch 变化；编码分支按解码顺序传递缓冲，展示时间 PTS 的重排也被误判为时间倒退。跨 generation 的缓存分段按现有安全规则输出空精确时间字段，Agent 因此拒绝取证。

## 需求与约束

- `generation` 标识源时间坐标发生变化，不因展示/分析正常跳帧或编码 PTS 重排而递增。有效时间继续向前时，单独的 `DISCONT` 不建立新 epoch；没有有效时间且出现 `DISCONT` 时仍保守重置。
- 解码后的帧以 PTS 检测实际时间倒退；编码缓存以 DTS 检测解码顺序中的时间倒退。编码 DTS 缺失时不以可能重排的 PTS 冒充解码时序。
- 缓存分支在 MP4 mux 前使用 `h264timestamper` 从 H.264 重建 DTS，避免 RTSP 缺失 DTS 时被 muxer 拉长时间轴。验收必须比较媒体实际时长和源 PTS 区间，并核对事件中心画面，不能仅验证文件存在或可解码。
- 初次取得推理几何只初始化状态；后续真实几何变化仍重置 generation 和跟踪状态。
- sidecar 的展示区间根据同一 generation 内的最小 PTS、最大有效帧结束时间计算。跨 generation、无时间或不完整的元数据继续保持 fail closed，不伪造精确证据。
- 若已观测到封口 running-time 对应的同 generation 边界帧，以该帧的真实 PTS 作为半开区间终点，避免 30 FPS 标称帧时长的纳秒舍入制造分段断缝；不在 Agent 中放宽连续性判断。
- SIGINT、SIGTERM 和窗口关闭请求通过同一受控停止路径发送 EOS，保留 bus 消费和缓存对象，等待终端 EOS 后再进入 `GST_STATE_NULL`，使 splitmuxsink 有机会封口并发布 sidecar。
- 受控停止重复请求幂等；排空默认最多等待十秒。EOS 拒绝或超时返回 `RuntimeFailure`，阶段为 `pipeline.shutdown`，不得报告成功完成。

## 接口与生命周期

- `SsvTimelineCursor::on_buffer` 保留签名，明确传入的是调用分支的顺序时钟；`DISCONT` 不再等价于有效时间坐标重置。
- `SsvRunAttemptOptions.shutdown_timeout` 是内部运行选项，不新增 YAML 配置。`SsvRunAttempt` 持有并销毁排空超时源。
- 不改变 Redis 事件、sidecar schema、SQLite、Agent/Web DTO、证据读取的安全边界以及 pipeline/service/window 的所有权。
- 缓存拓扑增加内部元素 `evidence-cache-timestamp`，要求运行环境提供 GStreamer `h264timestamper`，缺失时走现有能力检查失败路径。

## 验收

1. 真实 leaky queue 确实丢帧、PTS 持续向前时，推理 generation 保持稳定。
2. 编码缓冲 DTS 连续、PTS 重排时，实际 splitmuxsink 产出的 finalized sidecar 仍有有效 generation 和精确 PTS 区间。
3. 真实 PTS 倒退、flush、几何变化仍能重置；无有效时钟的 discontinuity 继续保守处理。
4. 受控信号使 EOS 到达 sink 后才停止；无法排空时明确失败。
5. 清空本项目事件流和账本后，以实际 RTSP、真实检测、Agent 与只读 Web API 重跑。停止 GST 后验证缓存、事件证据、复核任务及 Web 返回值，不把“触发事件”或“MP4 非空”单独当作通过条件。

## 非本阶段范围

不调整模型效果、跟踪算法、Agent 复核策略、Redis 版本升级策略或硬件解码契约；不重构整个多分支时间线，不修改其他工作区，不提交或推送。
