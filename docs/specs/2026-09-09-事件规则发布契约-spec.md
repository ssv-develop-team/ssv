# 事件规则发布契约规范

## 文档定位

本文定义实时检测生产端向 Redis 发布事件规则事实的配置和消息契约，解决 Agent
复验时“证据可用但事件登记规则未知”的问题。规则事实由事件生产端负责，Agent
只负责持久化、检索候选条款和复验，不从 RAG 结果反推事件登记规则。

## 目标

1. 每个新启动的检测 source 都必须显式配置事件规则。
2. `ssvpub` 将 source 的事件规则原样写入 Redis 事件 payload。
3. Agent 现有 `ReviewContext`、`EventLedger` 和 RAG 链路直接复用这些字段。
4. 规则事实与 RAG 候选保持独立，结果仍能追溯登记事实和规则引用的不同来源。

## 非目标

- 不在 Agent 内新增 `event_type -> rule` 映射表。
- 不从任意 RAG chunk 自动生成或覆盖 `rule_id`、`rule_version`、`rule_facts`。
- 不改变检测、跟踪、发布冷却或证据提取算法。
- 不为历史 Redis 消息回填缺失的规则事实；历史消息仍按原有未知语义处理。

## 配置契约

`sources` 中的每个 source 必须包含 `event_rule` 映射。当前配置只允许一个 source，
规则配置随 source 归属，便于未来扩展多 source：

```yaml
sources:
  - id: "camera-01"
    uri: "rtsp://localhost:8554/stream"
    event_rule:
      event_type: "person_without_helmet"
      severity: "high"
      rule_id: "GB26860-2011-5.2.2"
      rule_version: "GB/T 26860-2011"
      rule_facts:
        label_semantics:
          head: "未佩戴安全帽的头部（违规对象）"
          helmet: "佩戴安全帽的头部（合规人员）"
```

字段约束：

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `event_type` | 非空字符串 | 写入 Redis 的显式事件类型 |
| `severity` | 非空字符串 | 写入 Redis 的事件严重级别 |
| `rule_id` | 非空字符串 | 事件生产端选择的规则标识 |
| `rule_version` | 非空字符串 | 规则版本或标准版本 |
| `rule_facts` | JSON object | 只允许 YAML 映射及 JSON-compatible 标量、数组、嵌套映射；约定键见下 |

缺少 `event_rule` 或任一必需字段、`rule_facts` 不是映射、值无法转换为 JSON 时，
C++ runner 必须以配置错误退出，不启动会产生不完整事件的 pipeline。

规则事实的约定键：

| 键 | 用途 |
| --- | --- |
| `label_semantics` | 检测类别到语义的说明；既进入 Agent 复核上下文，也决定承载规范的条文能否排进规则检索候选 |

`rule_facts` 保持自由映射：C++ runner 只校验整体是 JSON-compatible 映射，不校验键集合；
其余键按登记事实原样保存。

`label_semantics` 是检索的主要杠杆：词法检索只对自然语言计分，单字符 token 的权重为 0，
条款号（如 `1.1`）不参与匹配，因此承载规范的条文能否进入候选取决于该键提供的自然语言。
复核的引用校验只接受本次预检索返回的候选 chunk，模型即使自行再检索，也无法引用候选之外的条文。

## Redis payload 契约

`ssvpub` 保留现有字段，并新增以下字段：

```json
{
  "type": "detection",
  "event_type": "person_without_helmet",
  "severity": "high",
  "rule_id": "GB26860-2011-5.2.2",
  "rule_version": "GB/T 26860-2011",
  "rule_facts": {
    "label_semantics": {
      "head": "未佩戴安全帽的头部（违规对象）",
      "helmet": "佩戴安全帽的头部（合规人员）"
    }
  }
}
```

`type` 保持现有发布消息类型，`event_type` 作为 Agent 的显式事件类型；不使用
`type` 覆盖显式 `event_type`。

## 所有权和处理边界

```text
YAML source.event_rule
        ↓
C++ config parser → pipeline builder → ssvpub
        ↓
Redis event payload
        ↓
EventConsumer → ReviewContext → EventLedger
        ↓
ReviewWorker：RAG 候选 + evidence 复验
```

事件规则字段是上游登记事实，RAG 返回的 `rule_citations` 是本次复验的候选条款。
二者可以指向同一规则，但不得互相替代或覆盖。

## 兼容和失败语义

- 新配置严格要求 `event_rule`，从源头阻止新事件缺少规则字段。
- 已存在的 Redis 消息、测试中直接构造的旧 payload 和历史 SQLite 事件不回填规则。
- Agent 对缺失字段保持 `unknown`，规则候选缺失时仍只能返回 `uncertain`。
- payload 序列化失败不得发布半成品消息；pipeline 应在配置阶段失败。

## 验收标准

1. 完整配置可加载，`event_rule` 字段和值类型被保留。
2. 缺少 `event_rule`、缺少必需字段和错误 `rule_facts` 类型均被拒绝。
3. `ssv_pub_build_event_payload` 生成的 JSON 包含五个规则字段，且嵌套事实类型不丢失。
4. pipeline builder 将 source 规则字段设置到 `ssvpub`。
5. Agent 现有上下文和 RAG 测试继续通过；不新增 Agent 侧规则映射。
