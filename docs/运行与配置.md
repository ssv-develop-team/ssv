# 运行与配置

本文是当前运行方式的入口。字段的完整约束仍以 `config/ssv.example.yaml`、
`docs/检测前端配置.md` 和 `docs/Agent配置.md` 为准；历史 `docs/specs/`、
`docs/plans/` 保留各自阶段的设计记录，不作为当前配置模板。

## 配置文件角色

项目有两类 YAML，不能互相替代：

| 文件 | 作用 | 是否提交 |
| --- | --- | --- |
| `config/ssv.yaml` | C++ runner 和 Python Agent 共用的运行配置 | 否，复制 `config/ssv.example.yaml` |
| `config/ssv.example.yaml` | 运行配置模板，包含 RTSP、推理、证据、Agent 字段 | 是 |
| `agent/config.yaml` | DeerFlow review worker 的模型和只读工具配置 | 否，复制 `agent/config.example.yaml` |
| `agent/config.example.yaml` | DeerFlow 配置模板；模型密钥只从 `agent/.env` 读取 | 是 |
| `agent/.env` | 模型 provider 的地址、模型名和密钥 | 否 |

首次准备运行配置：

```bash
cp config/ssv.example.yaml config/ssv.yaml
```

需要启用模型复核时，再准备 DeerFlow 配置：

```bash
cp agent/config.example.yaml agent/config.yaml
```

不要把 `config/ssv.yaml`、`agent/config.yaml`、`agent/.env` 或包含真实 RTSP 签名地址的临时配置提交到 Git。

## 配置选择和路径

统一 CLI 的 `./ssv run` 和 `./ssv agent` 支持显式 `--config PATH`。未显式指定时，项目配置查找顺序为：

1. `SSV_CONFIG_PATH`；
2. 项目根目录的 `ssv.yaml`；
3. 项目根目录的 `config/ssv.yaml`；
4. `/etc/ssv/ssv.yaml`。

`config/ssv.example.yaml` 不会被自动加载。

运行配置中的相对 Agent 路径以 `agent/` 目录为基准：

| 配置 | 默认值 | 用途 |
| --- | --- | --- |
| `agent.event_db_path` | `data/events.db` | SQLite EventLedger |
| `agent.output_dir` | `outputs` | 复核 JSON 和 Markdown 报告 |
| `agent.knowledge.rules_dir` | `knowledge/rules` | 版本化规则目录 |
| `agent.knowledge.qdrant_path` | `data/qdrant` | 本地 Qdrant 数据 |

例如默认报告根目录是 `agent/outputs`。只有配置中明确写入绝对路径时，产物才会写到其他目录。

## 最小运行流程

```bash
./ssv build --profile cpu
./ssv redis start
./ssv run --config config/ssv.yaml --headless
```

需要 Agent 消费 Redis 事件时，在另一个终端运行：

```bash
./ssv agent --config config/ssv.yaml
```

`./ssv inspect` 当前只检查构建验证插件 `ssvtemplate`；RTSP、解码器、编码器和 SSV 业务插件要用下面的 `gst-inspect-1.0` 命令单独检查。它不能代替真实 RTSP、模型、Redis 或外部 RTSP 服务联调。直接在 `agent/` 中执行 `python -m ssv_agent` 时，应显式传入 `--config`；它不会按统一 CLI 的项目根目录和 `/etc/ssv/ssv.yaml` 路径搜索。

## RTSP 拉流、分析和推流

### 输入拉流

当前配置契约支持一个 H.264 8-bit RTSP 输入：

```yaml
sources:
  - id: camera-01
    uri: rtsp://camera.example/stream
    codec: h264
    protocols: tcp
    decode:
      mode: auto
      device: auto
```

代码路径为 `rtspsrc -> rtph264depay -> h264parse -> decoder`。`decode.mode` 可选择 `auto`、`vaapi`、`nvdec` 或 `software`；`auto` 只根据实际 GStreamer factory 和 memory contract 选择，不把“系统有 GPU”当作硬件解码可用。

### 实时分析

开启以下字段后，解码帧进入检测、跟踪和事件发布分支：

```yaml
inference:
  enabled: true
  analysis_fps: 5
tracking:
  enabled: true
```

分析分支使用 `ssvinfer`、`ssvtrack` 和 `ssvpub`，事件通过 Redis Streams 交给 Agent。短时证据缓存由 runner 的 `evidence_cache` 连续写入，Agent 的 `recording_evidence` worker 从中提取事件上下文；具体字段见 [检测前端配置](检测前端配置.md) 和 [Agent 配置](Agent配置.md)。

### 推流到外部 RTSP 服务

SSV 使用 GStreamer `rtspclientsink` 作为**发布客户端**，不会在本机启动 RTSP server。目标地址必须已经由 ZLMediaKit、MediaMTX 或其他 RTSP 服务提供发布入口：

```yaml
display:
  enabled: true
  backend: rtsp
  rtsp:
    location: rtsp://127.0.0.1:8554/ssv
    encoded_passthrough: false
    burn_in_overlay: false
```

普通 RTSP 输出路径为：

```text
decoded branch -> videoconvert/caps -> H.264 encoder
               -> h264parse -> rtph264pay -> rtspclientsink
```

推理和推流可以同时运行。输出分支与分析分支并行；RTSP 发布失败由运行时作为 display 分支错误处理，不能据此认定推流已经成功。

### H.264 编码旁路

输入和输出都使用 H.264、且不需要烧录框时，可以启用：

```yaml
display:
  backend: rtsp
  rtsp:
    encoded_passthrough: true
    burn_in_overlay: false
```

这条路径从 `h264parse` 后复制编码码流，经 `rtph264pay` 和 `rtspclientsink` 发布，不对输出分支解码、改帧率或重新编码。分析仍可使用独立的解码分支，因此它适合“原视频推流 + 后台检测”。

### 烧录分析框

接收端需要在视频像素中直接看到检测框时：

```yaml
display:
  backend: rtsp
  rtsp:
    encoded_passthrough: false
    burn_in_overlay: true
```

这会在编码前插入 `ssvoverlay`，因此必须有可用的解码器、系统内存视频路径、overlay 插件和 H.264 encoder。`encoded_passthrough` 与 `burn_in_overlay` 互斥；默认 RTSP 输出不包含检测框元数据或像素框。示例 COCO `yolov8n.onnx` 只检测 `person`；若要展示安全帽结果，还需接入相应模型和规则。

## 能力判断

| 能力 | 当前项目代码 | 本机当前检查 |
| --- | --- | --- |
| RTSP 拉流 | 支持 | 已用真实设备流验证 |
| RTSP 拉流后推理/跟踪/Redis 发布 | 支持 | 2026-09-29 已用真实设备流验证软件解码与约 5 FPS 推理；自然事件触发及真实安全帽规则仍需验证 |
| RTSP 推流（重编码） | 支持 | 需要 `rtspclientsink`、`rtph264pay` 和 H.264 encoder；本机当前缺少 `rtspclientsink` |
| RTSP 推流（H.264 旁路） | 支持 | 仍需要 `rtspclientsink`；本机当前不能直接启动 |
| 推流同时分析 | 支持 | 代码和现有 builder 测试覆盖并行分析与 RTSP 分支；真实发布仍需外部 server 和 factory |
| SSV 自己作为 RTSP server | 不支持 | 由外部 ZLMediaKit/MediaMTX 提供 |

本机在 2026-09-30 的只读检查发现 `rtph264pay`、`openh264enc` 可用；设置项目构建插件路径后，`ssvinfer`、`ssvtrack`、`ssvpub`、`ssvoverlay` 可被发现。`rtspclientsink` 缺失。部署机器应重新检查所需 factory：

```bash
gst-inspect-1.0 rtspclientsink
gst-inspect-1.0 rtph264pay
gst-inspect-1.0 openh264enc
./ssv inspect
```

因此当前结论是：**项目架构和代码可以完成“RTSP 拉流 + 分析 + 推流”，当前主机已经验证拉流分析，但推流还缺 `rtspclientsink` 运行时插件，并且尚未用真实外部 RTSP server 完成推流验收。**

更多字段和故障排查见 [检测前端配置](检测前端配置.md)；Agent 的事件、证据、复核和报告见 [Agent 配置](Agent配置.md)。
