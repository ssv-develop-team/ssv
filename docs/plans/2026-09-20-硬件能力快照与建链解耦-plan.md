# 硬件能力快照与建链解耦实施计划

## 步骤 1：能力快照类型

- 在 `runner/pipeline/ssv_hardware_capabilities.hpp/.cpp` 增加
  `SsvCapabilitySnapshot`，保留 `SsvHardwareCapabilities` 作为 probe 原始结果。
- 保留 system probe 的 raw 结果接口，由 `prepare_run()` 封装为快照；测试
  factory 直接返回快照，查询接口保持 const。
- 为快照补充单元测试，确认 factory、ONNX Runtime 和 TensorRT 能力可以被只读查询。

## 步骤 2：plan 持有快照

- 在 `SsvPipelinePlan` 增加 `capability_snapshot`。
- `SsvPipelinePlan::resolve` 从快照解析 decoder、encoder、inference 和 caps，返回
  的 plan 持有本次运行所用快照。
- 删除接收 raw `SsvHardwareCapabilities` 的兼容重载，避免调用方绕过快照接口。
- 保持现有选择顺序、fallback 事件和纯 RTSP encoded passthrough 语义不变。

## 步骤 3：builder 消费 plan

- 移除 `SsvPipelineBuilder::build` 和
  `pipeline_internal::resolve_topology` 的独立 registry 参数。
- builder、factory registration 和 topology contract 全部读取
  `plan.capability_snapshot`。
- `SsvSystemRunAttemptFactory` 不再保存第二份能力 registry；pipeline 创建只消费
  plan 和 runner-owned inference service。

## 步骤 4：测试与文档

- 更新 pipeline、runtime 测试中的 fake probe、plan、builder 调用。
- 增加“同一快照贯穿 plan 与 builder”的断言。
- 运行格式检查、完整 Meson 测试、Agent 测试和统一测试入口。

## 步骤 5：推理 provider 快照

- 扩展 `SsvHardwareCapabilities` / `SsvCapabilitySnapshot`，保存并只读暴露
  `Ort::GetAvailableProviders()` 的规范化结果。
- 在 `prepare_run()` 的 capability probe 阶段获取 provider 列表；系统运行路径
  将列表传给 `ssv_inference_service_create()`。
- 扩展 inference 内部配置，使 `OnnxRuntimeBackend::load()` 优先使用外部快照，
  仅保留无快照的独立 public/test factory 兼容路径。
- 保留 provider session fallback、模型契约、cache 和 TensorRT engine 初始化的
  service/attempt 所有权，不把模型相关结果伪装成机器静态能力。
- 增加 provider 列表被 service/backend 消费以及复用语义的测试，并重新运行完整
  验证。

## 步骤 6：后端 plan 解耦

- 在 `runner/pipeline/ssv_pipeline_plan.hpp/.cpp` 增加 `SsvInferencePlan`、
  `SsvEncodePlan` 和 `SsvCodecPlan`，将推理 backend 与视频 codec backend 的选择
  从零散字段收口为可读的 plan。
- 在 `SsvHardwareCapabilities` / `SsvCapabilitySnapshot` 中表达 VAAPI、NVDEC/
  NVENC 和 software encoder 的 factory 能力；设备级 factory 必须保留对应的
  DRM/CUDA device 约束。
- RTSP 重编码优先选择同设备 hardware codec pair；pair 不可用时保留硬件 decoder
  并使用 SystemMemory 软件 encoder，形成混合路径。
- `runner/pipeline/ssv_pipeline_builder.cpp` 只按 `SsvCodecPlan` 组装解码、转换、
  overlay 和编码阶段，并对编码设备属性执行 contract 前的配置校验。
- 无编码器的显示/分析链标记为 `DecodeOnly`；NVDEC 到 CPU 消费者时显式插入
  `cudadownload`，硬件 NVENC 配对保持 `CUDAMemory`。

## 步骤 7：fallback 路径

- 扩展 `SsvRunFallbackState` 和 `ssv_pipeline_contract_recovery()`，硬件 codec
  pair 的创建或 contract 失败时，优先重建同一解码器 + 软件编码器的混合路径。
- 混合路径仍失败且 `decode.mode: auto` 时，沿已有策略回退到软件 decoder；显式
  硬件模式不静默降级。
- fallback 只重新解析 effective config 和 plan，复用同一个
  `SsvCapabilitySnapshot`，并发出可去重的 acceleration fallback 事件。

## 步骤 8：测试与文档

- 为能力快照、codec pair、混合 fallback、推理 backend 独立选择和 encoded
  passthrough 增加 focused tests。
- 更新 builder/runtime 测试，验证同设备 selector、SystemMemory 混合边界、
  CUDA 下载边界、fallback 顺序和 provider snapshot 复用。
- 运行定向 Meson 测试、完整 `meson test -C build --print-errorlogs`、
  `./ssv test`（若环境满足）和 `git diff --check`。
