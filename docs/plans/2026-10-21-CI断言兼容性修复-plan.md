## 步骤 1：断言兼容性修复与验证

### 涉及文件

- `docs/specs/2026-10-21-CI断言兼容性修复-spec.md`：新增，记录背景、约束、验收标准与非目标。
- `docs/plans/2026-10-21-CI断言兼容性修复-plan.md`：新增，记录实施顺序与实际验证结果。
- `runner/pipeline/tests/test_ssv_pipeline_plan.cpp`：修改，为五个包含列表初始化值的比较表达式增加圆括号，不改变类型、预期值或断言数量。

### 实施顺序

1. 核对工作区、PR HEAD、失败日志及相关测试函数，保留已有未跟踪目录。
2. 在不改写源文件的情况下，通过标准输入将完整测试源文件送入 C++20 语法检查；在标准头文件后临时使用单参数 `assert`，确认五处宏参数错误。
3. 新增本轮中文 spec/plan，再修正四个测试函数中的五处断言；不新增透传包装、测试框架或生产接口。
4. 对同一完整源文件重复单参数宏语法检查，要求由失败变为通过。
5. 重新编译并运行目标测试，随后运行完整 C++ 构建与测试；不为其他失败扩大修改范围。
6. 检查代码差异只包含五处括号修正，运行空白检查并记录验证结果。全部变更保持未暂存，供人工审阅。

### 验证方式

单参数宏验证只在输入编译器的数据流中覆盖 `assert`，使用 `-std=c++20 -fsyntax-only`，保留原测试源文件不变。该检查验证此次宏参数解析问题，不代替 Ubuntu CI 的完整执行。

目标及完整回归使用现有 Meson 构建目录：

```bash
meson compile -C build -j 2 ssv-pipeline-plan-test
meson test -C build --no-rebuild --print-errorlogs ssv-pipeline-plan
meson compile -C build -j 2
meson test -C build --no-rebuild --print-errorlogs --num-processes 2
git diff --check
```

仓库没有配置 C++ formatter，本轮保持现有排版，不引入新工具配置。验证中出现的动态库缺失、RTSP 链接失败或其他问题必须单独报告；远端 CI 只有在获准提交、推送并实际重跑后，才能确认新的状态。
